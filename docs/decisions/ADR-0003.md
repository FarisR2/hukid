# ADR-0003 — Contrato y laboratorio de autenticación de consola

- Estado: adoptado para laboratorio AUTH-T02; producción pendiente de validación institucional y proveedor.
- Fecha: 2026-11-03.
- Alcance: superficies nuevas BFF/Management de FEAT-001; no altera wallet, Events ni emisión.
- Complementa [ADR-0002](ADR-0002.md); no promueve el perfil HukID desde draft.

## Decisión

1. Materializar un OpenAPI 3.1 de consola y schemas propios, diferenciados del OpenAPI histórico ausente. Los handlers no están implementados por existir el contrato.
2. Mantener BFF Go del mismo origen, sesión opaca server-side y Management Bearer operator. La procedencia humana se expresa mediante el claim privado nuevo `hukid_grant=authorization_code`, conservado tras refresh; no se redefine la clase integration/OID4VCI.
3. Fijar `operator:read` como scope mínimo del contexto propio. Los roles/capacidades locales no autorizan recursos ajenos ni sustituyen scopes, membership o issuer scope. Mutaciones de miembros/invitación requieren USR-T01 y step-up.
4. Usar `oidc-provider` 9.13.3 exclusivamente como dev dependency y fixture de laboratorio, con JWKS ES256, secreto de cliente y clave de interacción generados en memoria. Solicitar Code + S256 PKCE y consentimiento para offline access. No Docker ni claves estáticas.
5. Simular interacción humana y evidencia `pwd`/`otp`/ACR test desde el harness, protegida por flags explícitos y secreto de ejecución. Esto prueba emisión/validación de claims, no factores reales ni un proveedor productivo. El fixture no se importa desde `src` ni se inicia con Platform.
6. Centralizar duraciones y allowlists test en configuración completa, sin defaults; validar relaciones y rechazar su carga en producción antes de abrir el listener. Los valores de sesión son propios de HukID y exclusivos de laboratorio.
7. Usar Problem Details seguro, correlación, no-store, CSRF synchronizer y Origin exacto en el contrato BFF. El único token de propósito CSRF permitido en `/me` no es access/refresh token.
8. Fijar el modelo lógico `tenancy`/`console_auth` sin inventar DDL original. AUTH-T03 creará migraciones nuevas y demostrará RLS; AUTH-T04–T07 implementarán validación, sesión, concurrencia y protecciones HTTP.
9. Resolver la diferencia entre la prohibición general de tokens recuperables del resumen de seguridad y la custodia cifrada exigida por FEAT-001: hashes para verificación; envelopes cifrados temporales para PKCE/access/refresh que deban recuperarse. Nunca claro, ni reentrega a partir de un hash. La precisión se limita al BFF y conserva las reglas de ofertas.

## Consecuencias y límites

Se añaden dependencias Node sólo de desarrollo: el backend Go conserva biblioteca estándar para esta tarea. Las pruebas criptográficas son del IdP y del verificador de laboratorio, no del futuro middleware de Management. No hay identidad/email real, proveedor productivo, secretos persistidos ni bypass de producción.

El contrato exige audience operator escalar; rechaza también arrays de un elemento como restricción propia de consola. El perfil sólo exigía rechazo de audience múltiple: esta precisión no se aplica retroactivamente a otros productos o clases de token.

Antes de producción deben aprobarse issuer/JWKS/client auth, algoritmos soportados, MFA/step-up reales, TTL/rate limits, cookies HTTPS, almacenamiento de secretos, retención y operación. Cambiar proveedor o mapping de claims requiere nueva evidencia y revisar este contrato; no se relaja el perfil para adaptar un IdP.
