# ADR-0004 — Foundation PostgreSQL de consola

- Estado: adoptado para AUTH-T03 y validado en laboratorio; operación productiva pendiente.
- Fecha: 2026-11-03.
- Alcance: persistencia propia HukID Console; no DDL histórico de issuer, Events ni wallet.
- Complementa [ADR-0003](ADR-0003.md) y el [modelo HukID](../03-design/hukid-data-model.md).

## Decisión y evidencia

1. Materializar dos migraciones nuevas forward-only: foundation y aislamiento. Usar runner embebido con SHA-256, transacción por archivo/ledger y advisory lock. Normalizar sólo CRLF para checksums portables. No reescribir ni fabricar migraciones externas.
2. Usar pgx v5.12.0 para PostgreSQL. Se eligió esa versión publicada para incluir las correcciones documentadas por el mantenedor; no se hereda un driver de Events.
3. Separar credenciales/roles para datos tenant, descubrimiento de operador y store de sesión. Runtime sin ownership, superuser ni BYPASSRLS; rechazar también privilegios heredados peligrosos.
4. Aplicar RLS forzada y actor/tenant con configuración local a la transacción. El descubrimiento usa funciones SQL mínimas con owner NOLOGIN/NOBYPASSRLS y policies por actor, sin bypass general ni directory endpoint.
5. Materializar identidad `(issuer, subject)`, membership única y FK compuestas para roles, actor/familia/deadline de sesión, selección de tenant y audit/outbox. Los registros globales de identidad/sesión conservan su frontera separada; no se les inventa un tenant único.
6. Guardar sólo hashes y envelopes recuperables con nonce/key version; invalidar una generación o consumir una transacción exige purgar su ciphertext en la misma actualización. El cifrado productivo y la coordinación de familias se implementan en sus tareas, sin inferirlos de las CHECK SQL.
7. Exponer provisioning sólo como CLI de test con flags/destino explícitos y administrador aislado; nunca registro público. Bootstrap sintético atómico, auditable y repetible sin regrant.
8. Probar con PostgreSQL 18.6 portable local, passwords efímeros y bases/clúster nuevos. No Docker ni servicios globales requeridos. El harness detiene únicamente su servidor y borra únicamente recursos creados por la prueba.

## Consecuencias

Los grants de lectura actuales sólo cubren metadata/contexto propios. Directorio y mutaciones de miembros, auditoría runtime, terminalidad/reinvitación, último admin y alcance issuer requieren sus gates futuros. Las policies no autentican al actor: AUTH-T04/T05 deben aportar identidad verificada y revalidar autorización.

Roles son globales al clúster; crear/actualizar esquemas exige una credencial de migración distinta de runtime. Este incremento sólo automatiza un laboratorio local descartable, no aprueba TLS/backup/rotación/retención ni un servicio PostgreSQL productivo. No agrega endpoints HTTP ni cambia los contratos externos.
