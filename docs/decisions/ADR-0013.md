# ADR-0013 — Directorio autorizado y cursores opacos

- Estado: adoptado para laboratorio USR-T03; producción sigue bloqueada.
- Fecha: 2026-11-05.
- Alcance: cuatro GET de FEAT-002 sobre ADR-0011 y ADR-0012.

## Contexto

El schema 0007 prepara miembros e invitaciones con información sensible. RLS aísla tenant, pero no comprueba capacidad de lectura. Un cursor reutilizable o una respuesta de directorio demasiado amplia podrían permitir enumeración o exponer destinatarios.

## Decisión

1. Registrar sólo las cuatro lecturas de lista Management/BFF existentes en el contrato. Reutilizar verificación operator, identidad y sesión AUTH; no crear login ni servicio users distinto. BFF exige el tenant seleccionado por AUTH, además de pertenencia viva.
2. Conectar un pool con credencial hukid_members_runtime independiente y configuración test opcional completa. Dentro de una transacción de sólo lectura con snapshot repetible, comprobar tenant/membership activos y capacidad desde la matriz antes de consultar proyecciones mínimas. Conservar RLS y variables transaccionales locales.
3. Usar keyset ascendente createdAt/UUID y cursor AES-256-GCM con clave externa propia, ligado a actor/tenant/operación/filtros/límite/versión/deadline. Conservar deadline al continuar, reautorizar cada petición y rechazar alteración o cambio de contexto con invalid_cursor. No prometer snapshot entre páginas.
4. No descifrar destinatarios para listar: recipientHint fijo `***`, o `redacted` al vencer retención/faltar ciphertext. Filtrar y representar expiración efectiva sin escribir. Mantener campos mínimos, errores seguros y headers privados; sin tokens, hashes, envelopes ni claims.
5. Precisar el contrato de filtros: query es un prefijo UUID canónico, no una búsqueda por email; parámetros vacíos/repetidos/desconocidos son 400 y valores fuera de dominio son 422. Declarar ese 422 en las cuatro operaciones GET.

## Consecuencias y límites

La [referencia USR-T03](../03-design/console-members-directory.md) concentra comportamiento, configuración, pruebas y retirada. No cambia migraciones aplicadas, emisión de scopes, capacidades ni clases de token. El contrato pasa de doce operaciones pendientes a cuatro lecturas implementadas y ocho mutaciones contract-only. No añade consulta individual ni UI.

Un cambio concurrente posterior al snapshot de una lectura se aplica en la siguiente petición; el cursor no guarda permisos. La máscara fija evita recuperar PII, pero no ayuda a distinguir destinatarios; la UI futura debe hacer explícita esa limitación o acordar un cambio revisado. La rotación de clave requiere reiniciar la paginación. No hay estado de cursor persistido ni revocación individual de continuaciones.

La credencial members tiene los permisos preparados por 0007, aunque las rutas actuales son de lectura. Rate limiting específico, carga, operación productiva, aceptación/entrega y UI siguen pendientes. Retirar configuración USR desregistra las rutas al reiniciar y conserva datos/evidencia y AUTH.
