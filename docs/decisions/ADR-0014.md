# ADR-0014 — Invitaciones cifradas y proveedor sintético idempotente

- Estado: adoptado para laboratorio USR-T04; producción sigue bloqueada.
- Fecha: 2026-11-05.
- Alcance: creación/revocación Management/BFF, worker por tenant y migración 0008.

## Contexto

ADR-0011 fija contrato, TTL y replay. ADR-0012 prepara hash, destinatario/envelope cifrados, lock y evidencia. Las lecturas de ADR-0013 no entregan invitaciones. El incremento necesita una entrega comprobable sin seleccionar un proveedor productivo ni ampliar AUTH.

## Decisión

1. Conectar las cuatro operaciones de creación/revocación con autorización viva y MFA firmado. Transportar un deadline de evidencia validada para revalidar freshness bajo lock sin I/O OIDC en la transacción.
2. Compartir el lock tenant existente; comandos usan try-lock y 409/Retry-After ante contención. Mutación, reemplazo, idempotencia, audit y outbox se confirman juntos; replay reautoriza y no genera evidencia duplicada.
3. Usar claves externas separadas para cifrado de invitaciones y HMAC tenant/email; separarlas también de AUTH y cursor. No habilitar escrituras al configurar sólo las lecturas. Mantener el rechazo cerrado de issuerIds sin fuente confiable.
4. Ejecutar un worker explícito por tenant, fuera del API y sin un escaneo global. El puerto exige deduplicación duradera por tenant/invitación/generación. La entrega externa ocurre sin lock tenant y el resultado local vuelve a comprobar elegibilidad.
5. Añadir mediante expand 0008 los recibos del proveedor falso con RLS y digest sin payload. No modificar migraciones publicadas ni publicar PII por outbox. Una instancia nueva del proveedor reconoce el recibo anterior tras una caída.
6. Purgar material recuperable y fingerprints por deadlines; conservar evidencia, hash y recibos. Mantener aceptación y entrega como estados independientes.

## Consecuencias y límites

La simulación verifica persistencia y deduplicación, pero no envía email, verifica destinatarios ni implementa aceptación. Una revocación no retira un mensaje ya aceptado por el proveedor. Sin envelope vigente no hay reenvío recuperando un hash. El operador debe crear una invitación nueva.

El worker usa la credencial members backend existente, IDs explícitos confiables y ambiente test. No hay scheduler, transporte real, SLA de purga, rotación de claves, carga/restore ni operación productiva. Se mantiene el expand al deshabilitar rutas/worker. No se cambia la política de ofertas de credenciales ni el perfil draft.
