# ADR-0026: Native Keycloak operator profile for the local console

- Status: accepted for the local laboratory implementation requested on 2026-11-09.
- Date: 2026-11-09.

## Context

The [first real-flow audit](../05-delivery/reviews/local-flow-2026-11-09.md) found RS256/JWT tokens, empty AMR, ACR 1 and missing operator claims. The [existing contract](../03-design/console-auth-contract.md) requires ES256, at+jwt, an exact scalar operator audience, registered client, human grant provenance and signed MFA evidence. [ADR-0025](ADR-0025.md) remains the historical local-profile proposal; its unverified provider assumptions must not override the executable contract.

## Decision

1. Reconcile a dedicated native Keycloak 26.8.2 client and browser flow through the administrative REST API. Authenticate each administrative command independently; do not depend on persisted kcadm sessions.
2. Keep the backend validator and public APIs unchanged. Use the native RFC 9068 header option, a persistent P-256 signing provider, ES256 client signing attributes and an explicit operator audience mapper. Preserve the signing key on reconciliation; do not rely on an ephemeral fallback key. Exclude default roles/audience scopes from this dedicated client.
3. Use required password and OTP authenticators. AMR values are references attached to completed executions with validity bounded by the local absolute session lifetime. A conditional LoA 2 subflow with zero reuse age records ACR only after its flow succeeds. The backend still requires both methods and fresh evidence for privileged operations.
4. Client-specific constants may identify client_id and the operator class. The original human grant marker is bound to an exclusively Code+refresh client: password, implicit, service accounts, device, CIBA, JWT authorization grant and standard token exchange are disabled. This is an administrative trust invariant, not a claim supplied by the browser. No other client inherits these mappings. MFA claims and auth_time are never hardcoded.
5. Preserve original grant/authentication evidence across refresh and enforce refresh rotation. TOTP enrollment alone does not count as an executed OTP authenticator: its first callback may be denied, and a complete subsequent password+OTP login is required. The UI's existing bounded recovery path is used.
6. Provision five separate PostgreSQL runtime logins and independent cursor/invitation keys. Updating an existing local installation preserves passwords, enrolled factors, data and keys. Bootstrap remains idempotent and never restores revoked access.
7. Add an opt-in real-provider gate with its own realm, PostgreSQL cluster, API and console. It may use the already running local Keycloak server but never uses the persistent application database. Delete only the owned realm and stop only owned test resources.

## Consequences

The local operator token shape is a deliberate application profile, not Keycloak's defaults or a claim of universal OIDC compatibility. Drift must be reconciled or rejected before application startup. Native provider configuration avoids introducing a custom Java extension or weakening token verification.

Detailed settings, reproduction and acceptance are maintained in [the local Keycloak reference](../03-design/console-local-keycloak.md). Production, real mail delivery, key rotation, restore/DR and credential/wallet conformance remain outside this decision.
