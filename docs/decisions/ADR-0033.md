# ADR-0033 — Demo sintética de recepción wallet, aislada del perfil productivo

- Estado: decidido para laboratorio por aprobación del owner; implementación T2 contractual.
- Alcance: demo de taller ficticio, no académico y no habilitante, para recepción Android.
- Relacionado: [contrato ejecutable](../03-design/wallet-laboratory-contract.md),
  [perfil draft](../03-design/hukid-profile.md), [compatibilidad ADR-0031](ADR-0031.md).

## Decisión

Se fija `lab.workshop.vc-jwt.v1`, subject cerrado y artefactos v1 offline derivados
únicamente del origen HTTPS configurado. No se fija ningún dominio externo desplegado.
La definición no declara status: no aplica, sin simular comprobación de revocación.
La validación tipada del schema local del subject no es verificación criptográfica,
trust, vigencia ni validación genérica de VC JSON Schema/expansión JSON-LD.

Excepciones explícitamente aprobadas: T3 podrá firmar de verdad con una clave efímera
propia del issuer, sólo en memoria y sólo laboratorio, en lugar de KMS no exportable;
el issuer podrá tener origen HTTPS de laboratorio en lugar de `issuer.hukid.pe`.
No autoriza exportar claves, persistir privadas, desactivar validación TLS ni reutilizar
la excepción HTTP de consola. El consumidor configura el issuer y su clave confiable;
la credencial no aporta autoridad para elegir claves/JWKS. Sin fallback productivo.

## Consecuencias y límites

T2 no firma ni sirve HTTP. T3 debe implementar proof/challenge, firma y trust de issuer;
T4 validación/consentimiento Flutter; T5 cifrado local con Keystore no exportable,
descifrado controlado y comprobación tras reinicio. Las excepciones no eliminan T5.
Se descartan certificado académico, datos personales, status ficticio y relajación
del verifier compartido. No cambia la prioridad POS, no cierra HK-043 ni el gate de
conformance; no implica emisión productiva, interoperabilidad o wallet terminada.
