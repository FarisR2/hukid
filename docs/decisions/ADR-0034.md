# ADR-0034 — Custodia de la clave de firma del verifier por tenant (FEAT-004, VER-T11)

- Estado: **propuesta**. El owner eligió la **opción A** (HukID custodia cifrada, por tenant) el 2026-11-17 y pidió redactarla con los límites de este texto. Eso no es una aprobación formal del ADR escrito: los detalles de cifrado, rotación y `x5c` siguen siendo propuestos hasta que el owner apruebe este documento. Revocable.
- Fecha: 2026-11-17.
- Relacionado con: [ADR-0033](ADR-0033.md) #7 (que dejó este punto abierto), [ADR-0030](ADR-0030.md) (independencia del módulo de verificación), [ADR-0032](ADR-0032.md), [perfil HukID](../03-design/hukid-profile.md) §10 y §12, [tareas](../features/FEAT-004-credential-verification/tasks.md).

## Contexto

El request object de OpenID4VP se firma con una clave del verifier. En el laboratorio es una sola clave por proceso, tomada del entorno. ADR-0033 #7 fijó que `client_id`, `response_uri` y la clave pertenecen al tenant, pero dejó abiertas su custodia, su rotación y el `x5c`/`x509_san_dns`. Sin esa decisión T11-d no puede firmar requests por tenant.

## Decisión

1. **Custodia (opción A).** HukID guarda la clave de firma del request object de cada tenant, **cifrada y aislada por tenant**. La clave es del tenant; HukID solo la custodia. Quedan descartadas la identidad única de HukID para todos los tenants (contradice el perfil §10) y la firma externa por KMS/HSM del tenant (opción C), sin perjuicio de revisarla más adelante.
2. **Cifrado.** Se cifra con una clave maestra suministrada desde fuera del código y del repositorio, como las demás claves del proyecto. Este ADR no elige un KMS ni un gestor de secretos productivo.
3. **Acceso.** Solo el rol de runtime de verificación puede usar la clave, y solo para firmar. La clave privada nunca sale por API, contrato, log, auditoría ni mensaje de error. Ningún rol de operador ni de consola la lee.
4. **Rotación.** Un tenant puede tener varias versiones a la vez: una **activa** que firma y otras **en retiro** que solo validan lo ya emitido. Cada sesión guarda el `kid` con el que se firmó. Una versión en retiro se elimina cuando no queda sesión vigente que la use, dentro del plazo de retención de ADR-0033.
5. **`x5c` / `x509_san_dns`.** El certificado lo aporta el tenant, porque el perfil §10 y §12 lo sitúan en su lado. HukID lo guarda y comprueba que su clave pública coincide con la clave custodiada y que no está vencido. HukID no emite certificados.
6. **Aislamiento.** El modelo de datos sigue el patrón de la migración `0013`: `tenant_id` y RLS con `tenancy.current_tenant()`. Un tenant no puede leer, usar ni rotar la clave de otro.

## Qué no decide

- La clave privada de firma de cada emisor ni el puerto KMS (decisión abierta #2).
- La elección de un KMS o gestor de secretos productivo, ni la rotación de la clave maestra.
- El esquema exacto de tablas ni el algoritmo de cifrado; se fijan en T11-d con sus pruebas.
- El procedimiento de alta de la configuración y del certificado por el tenant (API o consola).
- La interoperabilidad con un verifier o wallet externo ni el conformance gate del perfil §12.
- Producción: este diseño solo vale para laboratorio mientras la gestión de secretos siga sin decidirse.

## Alternativas consideradas

- **B) Identidad única de HukID.** Más simple, pero contradice el perfil §10: todos los tenants compartirían identidad ante el wallet.
- **C) El tenant firma externamente (KMS/HSM).** Mayor control del tenant, pero exige un puerto de firma remoto y alta disponibilidad por tenant antes del piloto. No se descarta para más adelante.

## Consecuencias

- T11-d queda desbloqueada en cuanto a la clave: puede firmar requests por tenant y mapear `state` a `session_id`.
- HukID asume la responsabilidad de custodiar material de firma ajeno: sin gestión de secretos productiva, nada de esto es apto para producción.
- Hasta tener código y pruebas de aislamiento entre tenants, nada de esto se considera implementado ni verificado.
