# ADR-0035 — Política de acceso `issuance:read` para consultas administrativas de solicitudes y credenciales (FEAT-005)

- Estado: **aprobado y ejecutado** en [capabilities.json](../../src/platform/contracts/capabilities.json) y [dashboard-metrics.json](../../src/platform/contracts/dashboard-metrics.json).
- Fecha: 2026-11-18.
- Relacionado con: [FEAT-005](../features/FEAT-005-issuer-operations/spec.md), [contrato del dashboard](../03-design/console-dashboard-contract.md), [administración del issuer](../03-design/console-issuance-management.md), [perfil HukID §6](../03-design/hukid-profile.md), [ADR-0031](ADR-0031.md).

## Contexto

Los endpoints privados `GET /v1/operator/tenants/{tenantId}/issuance-requests` y `GET /v1/operator/tenants/{tenantId}/credentials`, sus rutas BFF equivalentes (`/console/api/tenants/{tenantId}/...`) y las vistas React de **Solicitudes** y **Credenciales** ya están implementados en código. Sin embargo, `issuance:read` permanece dentro de `reservedCapabilities` en [dashboard-metrics.json](../../src/platform/contracts/dashboard-metrics.json) y sin asignación a roles en [capabilities.json](../../src/platform/contracts/capabilities.json), por lo que las vistas y lecturas quedan denegadas (`403`) hasta contar con una decisión explícita del owner.

## Decisión propuesta (plan de integración)

1. **Separación de clases de token (Perfil §6):**
   - La capability de operador `issuance:read` autoriza exclusivamente a un operador humano autenticado vía sesión BFF / token `operator` hacia `privateapi.IssuanceAdminHandler`.
   - Se mantiene totalmente separada del scope OAuth2 M2M `issuance:read` de clientes de integración (`oid4vcihttp`). Un token M2M nunca accede al BFF ni a `/v1/operator/...`; un operador nunca accede a claims ni payload OID4VCI.

2. **Asignación por rol y alcance por emisor:**
   - `tenant_admin`: recibe `issuance:read` para consultar el resumen operativo de solicitudes y credenciales de cualquier emisor perteneciente a su tenant activo (con filtrado opcional por `issuerId`).
   - `issuer_operator`: recibe `issuance:read` **únicamente** cuando se cumple `filter.IssuerID != ""` y `slices.Contains(opCtx.IssuerIDs, filter.IssuerID)`. Si `opCtx.IssuerIDs` está vacío o el `issuerId` no le fue asignado, el Management API devuelve `403`.
   - `support_readonly`: **no recibe** `issuance:read` en esta etapa (conserva únicamente `dashboard:read` salvo nueva aprobación).

3. **Minimización estricta de datos (`ISS-FR03`, `ISS-FR04`):**
   - Las respuestas de listado siguen siendo metadata-only (`requestId`, `issuerId`, `clientId`, `credentialDefinition`, `configurationId`, `offerState`, `issuanceState`, `credentialId`, `desiredStatus`, `publishedStatus`, `statusVersion` y timestamps).
   - Quedan prohibidos en las respuestas: `claims`, `claims_ciphertext`, `credential` (JWS), `digest`, `source_reference`, URI de oferta y códigos pre-autorizados.

4. **Impacto y coordinación con el Dashboard (`DASH-T05`):**
   - Retirar `issuance:read` de `reservedCapabilities` en [dashboard-metrics.json](../../src/platform/contracts/dashboard-metrics.json) afecta los contratos validados por `tests/auth/dashboard-contracts.test.mjs`.
   - Antes o junto con el cambio en `capabilities.json`, se debe elegir una de dos rutas compatibles en el mismo PR:
     1. Conectar las consultas SQL reales de `createdRequests` e `issuedCredentials` en `internal/adapters/postgres/dashboard.go` (dejando `status:read` reservada si `pendingStatusChanges` aún no se conecta).
     2. Mantener la distinción explícita entre métricas aún no conectadas (`unavailable / source_not_connected`) y `notAuthorized`, actualizando las aserciones y fixtures de `tests/auth/dashboard-contracts.test.mjs` de forma acorde.

5. **Plan de ejecución al aprobar este ADR:**
   1. Cambiar estado de este documento a **aprobado** con fecha y confirmación del owner.
   2. Añadir `"issuance:read"` a `roles.tenant_admin` y `roles.issuer_operator` en [capabilities.json](../../src/platform/contracts/capabilities.json).
   3. Actualizar [dashboard-metrics.json](../../src/platform/contracts/dashboard-metrics.json) y coordinar las consultas SQL o pruebas contractuales en `tests/auth/dashboard-contracts.test.mjs`.
   4. Agregar casos positivos (`tenant_admin` e `issuer_operator` acotado) y negativos (`support_readonly` → `403`, `issuer_operator` con emisor ajeno → `403`) en `issuance_admin_test.go`, `issuance_store_integration_test.go` y `tests/browser/issuance.py`.
   5. Ejecutar `npm run check`, `npm run build`, `npm run test:postgres` y `npm run test:browser`.

## Qué no decide

- No habilita acciones administrativas de status (`suspend`, `reactivate`, `revoke`) para operadores (`ISS-FR06` / `status:write` permanece exclusivo M2M).
- No concede `issuer:read`, `definition:read` ni `status:read`.
- No define la vista **Ajustes** ni el payload de negocio del segundo vertical.

## Consecuencias

- Permite revisar y aprobar el alcance de `issuance:read` con trazabilidad explícita antes de modificar `capabilities.json`.
- Mantiene intactos los contratos actuales (`npm run test:auth` 19/19) mientras el owner revisa la propuesta.
